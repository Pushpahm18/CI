# Change Notes and Audit Trail - proposed design (NOT approved, nothing created)

Status: design only. No table has been created and no code depends on these tables. Add/Edit/Import writes stay disabled until you approve this design and the tables exist.

## Why the existing schema cannot hold it
- `ci_main` keeps only created_by / created_date / modified_by / modified_date: no history, no notes.
- `ci_login_history` records sign-in events, not row changes.
- Delta table history shows that a version changed, not who changed which field to what, and has no Change Note.

## Proposed tables (both in corp_marketing_dev.ci, append-only)

### ci_change_note
| Column | Type | Meaning |
|---|---|---|
| note_id | STRING | UUID, generated by the server before writing |
| ci_id | STRING | the ci_main.ci_id this note belongs to (full UUID, never the display ID) |
| change_type | STRING | Add, Edit or Import |
| note_text | STRING | the mandatory Change Note (app enforces non-empty, max 2000 characters) |
| batch_id | STRING, nullable | the same UUID for every row of one import or bulk action |
| created_by | STRING | the actor's name, from ci_user_management (never from the request) |
| created_by_email | STRING | the actor's email, from the verified session |
| created_on | TIMESTAMP | server UTC time |

### ci_audit_trail
| Column | Type | Meaning |
|---|---|---|
| audit_id | STRING | UUID, generated by the server |
| ci_id | STRING | the ci_main row changed |
| note_id | STRING | links to ci_change_note (the note that explains this change) |
| batch_id | STRING, nullable | same as the note's batch |
| operation | STRING | Add, Edit or Import |
| field_name | STRING | the ci_main column, e.g. fab_region |
| old_value | STRING, nullable | value before, as stored text; NULL for an Add |
| new_value | STRING, nullable | value after, as stored text |
| changed_by | STRING | actor name |
| changed_by_email | STRING | actor email |
| changed_on | TIMESTAMP | server UTC time |
| source | STRING | Form or Import |

## Relationship to ci_main
`ci_id` is a logical link. Delta tables here enforce no foreign keys, so the application checks the ci_id exists in `ci_main` before writing a note or audit row. Rows are only ever inserted: the CI write guard would allow INSERT / MERGE-insert on these two tables and no UPDATE or DELETE.

## Old and new values
One audit row per changed field. An Edit records only fields whose value actually changed. An Add records every populated field with old_value NULL, including the derived Fab Region and Revenue. Values are the stored text (Wafer Size is recorded as the stored number, for example 300.0; the screen shows the approved label).

## Change Notes and edits
Every Add, Edit and Import row needs a note. The note and all of that change's audit rows share one note_id, so "who changed what and why" is one join. An import writes one note per imported row (the old Notes column becomes the first note, as the BRD says) and one batch_id for the whole file.

## Who, when, and what operation
The actor comes from the verified session email resolved through ci_user_management (the same record the authorizer used); the timestamp is server UTC; the operation comes from the code path (form add, form edit, import). None of these is accepted from the browser.

## Who can read audit details
Only Corporate Marketing, enforced in the API (`GET /api/competitive-info/[id]/audit` uses the Corporate Marketing authorizer). Account Team gets 403 unless you explicitly approve more. No role queries the tables directly. Decision needed: may Account Team read Change Notes (not audit) for rows inside their own scope?

## Consistency when several records are involved
Delta has no transaction across tables, so the order is fixed and retries are safe:
1. Validate the whole request (permissions, scope, edit window, mandatory note). Nothing is written if any check fails.
2. Generate every note_id / audit_id up front.
3. Write the note and audit rows first (MERGE ... WHEN NOT MATCHED, so repeating the call cannot duplicate them).
4. Write the ci_main change last.
5. If step 3 fails, ci_main is untouched and the user sees an error. If step 4 fails after step 3, a compensating audit row (operation = Void, same note_id) is appended, and the user sees an error. Nothing is updated or deleted.
6. Import: rows are processed in chunks, each chunk in the same order; the batch_id lets a report reconcile any chunk that stopped part-way.

## Visible Record ID
Real values: `ci_main.ci_id` is a 36-character UUID (example 001c204f-f1bf-4a07-8103-f8758d283b5a). The BRD and prototype show IDs like CI-0001.
Recommendation: display `CI-` plus the first 8 characters of the UUID in upper case (example CI-001C204F). The first 8 characters are unique across all 500 existing rows, so this needs no new column and changes no stored ID; the database keeps using the full UUID everywhere. The app checks for a clash when a new row is created. Import accepts either the full UUID or the display ID, and rejects a display ID that matches more than one row.
Alternative needing a schema change: a stored sequential number (CI-0001 style). Not recommended without approval.
